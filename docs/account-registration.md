# Account registration

This feature is prepared offline. It does not change existing users, passwords,
database schema, migrations, grants, Supabase Data API settings or Render settings.
It requires separate review and deployment approval.
See the [production-readiness review](registration-production-readiness.md) for
hosted privilege evidence, the exact unapplied grant proposal and release blockers.

## Public registration

`POST /api/auth/register` accepts exactly `fname`, `lname`, `email`, `password` and
`passwordConfirmation`. The server resolves the existing
`Faculty / Student Organization Representative` role by its exact name. Accounts
are active immediately. There is no email verification, invitation or signup role
selector. An email address is not proof of campus membership. Public registration
therefore requires an explicit operational decision to allow unverified users to
make the existing Representative requests; it never gives them staff permissions.

Names are trimmed, well-formed Unicode, 1–60 code points, without control or format
characters. Emails use ASCII address syntax, are trimmed and saved in lowercase,
and have a 150-character limit. Sign in with that normalized address: existing
login behavior and all legacy account addresses are unchanged. Case-insensitive
duplicate checks include existing accounts. Creation uses a Serializable
transaction and the existing unique email constraint; concurrent conflicts are
reported without retrying. Existing mixed-case duplicates are not modified.

Passwords must contain at least 15 Unicode code points and at most 72 UTF-8 bytes,
without control characters; a small obvious-password denylist is applied. Spaces
are preserved, not trimmed or truncated. Bcryptjs uses cost 12. Use unique, strong
passphrases generated by a password manager. Confirmation must match exactly.
Neither password nor hash is returned. Registration does not issue a JWT: the new
user explicitly logs in through the unchanged login flow.

## Administrator staff creation

`POST /api/accounts/staff` accepts the same five fields. Existing JWT middleware
checks the current active database user and requires `System Administrator`.
The transaction rechecks that actor before creation, resolves the existing
`Facility/Maintenance Staff` role and creates only that role. Nonadministrators
receive 403; unauthenticated or inactive users receive 401. Public users cannot
choose any role, IDs, activation state or nested user fields. Missing role
configuration fails closed with 503. No roles are inserted automatically.

Account Management is visible only to administrators. The administrator chooses
an initial password and shares it directly with the intended staff member through
an approved private channel. The application does not generate, email, download,
log or persist plaintext credentials, and clears form passwords on success or
server failure. There is no claim of implemented password reset or forced first
login password change. Operators must consider a reviewed account recovery and
staff password-change workflow before broader rollout. Initial passwords remain
known to the creating administrator until changed through an authorized process.

## Abuse controls and errors

Public signup permits ten attempts per observed client address per hour, before
validation, hashing or database access. Staff creation permits twenty attempts per
verified administrator per hour. Both count failures, return 429 with Retry-After,
expire buckets and cap retained keys at 5,000. Stores are process-local: restarts
reset limits, and multiple instances do not share limits. A shared edge/store
limiter is required before scaling horizontally or relying on strong distributed
abuse prevention. This does not add login rate limiting.

The existing Express proxy trust configuration is unchanged. Untrusted forwarding
headers are ignored. Behind Render, multiple visitors may share a rate-limit key
if the app sees the proxy address. Review the real proxy chain and a narrowly
trusted client-IP strategy or edge limiter before public rollout; do not blindly
trust all forwarding headers. No IPs or request bodies are logged by this module.

Only fixed field labels/codes are returned for validation. Duplicates and unique
or serialization conflicts return a generic 409. Other database failures return
a fixed 500 without SQL or driver details. All responses use no-store. A 201 is
sent only after transaction success; an uncertain outcome must be checked by
trying login or asking the administrator before submitting again. Clients never
automatically retry account creation.

## Production prerequisites — no live changes performed

The restricted production login was deliberately provisioned for existing auth
reads and management workflows, not public user insertion. Before enabling these
routes, separately review and verify its ability to resolve the two role names,
read the explicitly needed user columns for actor/duplicate checks, insert only
the required user columns, use the users ID sequence and select the response
projection. Do not run the web application as postgres, grant PUBLIC/anon/
authenticated table access, or enable the Supabase Data API. Do not broaden user
UPDATE/DELETE, audit-log or migration-history privileges. This patch adds no
grants, roles, database routines or migrations. If required privileges are absent,
registration returns a sanitized error; deployment remains blocked until a
separately approved least-privilege provisioning design is verified. Consider a
reviewed role-constraining database routine instead of direct user INSERT grants
when strengthening the database-level boundary against a compromised runtime.

## Verification

Offline HTTP tests use injected Prisma mocks, real bcrypt and JWT validation to
exercise signup/login, staff authorization, nonstandard role IDs, unknown-field
rejection, duplicate/case handling, missing roles, rate limits, failure sanitation
and transaction outcome handling. UI tests cover navigation, request contracts,
validation, visibility toggles, success states, cleared passwords and duplicate
submission prevention. Mocks do not prove hosted permissions, concurrent
transaction behavior or proxy client-IP attribution. Desktop/mobile browser
review remains required.
The isolated PostgreSQL suite additionally passed all 57 checks, including real
restricted-runtime signup/login, Staff authorization, denied audit/private-column
access and concurrent case-variant duplicate prevention. This does not verify
hosted grants or Render client-IP attribution. No live signup, staff creation or
account modifications are part of this run.
