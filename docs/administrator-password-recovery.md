# IM101: local administrator password recovery

Use only in a trusted, private, non-recorded PowerShell 7.6.7 terminal from the repository root. This is a manual recovery utility, separate from the web server; it exposes no API and runs no provisioning or migration.

Your private `.env` (or existing process environment) must contain the correct V2 `DATABASE_URL`, with exactly `sslmode=verify-full` as its query string. Supported connections are the Supabase direct host or AWS session pooler on port 5432, database `postgres`. The operator supplies the V2 project reference independently from the Supabase dashboard; the connection must match that reference. This prevents a stale V1 configuration from being used. Do not supply credentials as command arguments.

The trusted CA must already be at `$HOME\Documents\IM101-Backups\supabase-v2-ca.crt`, or set `NODE_EXTRA_CA_CERTS` to its trusted local path before running. Obtain the certificate from the intended project's trusted dashboard/database SSL settings. Missing, invalid or non-CA certificates are refused. TLS chain and hostname verification stay enabled. Do not disable verification to resolve connection failures. The connection is built from explicit fields to prevent URL SSL options replacing the CA configuration; see [node-postgres SSL configuration](https://node-postgres.com/features/ssl) and [Supabase connection documentation](https://supabase.com/docs/guides/database/connecting-to-postgres).

Run privately:

```powershell
pwsh -NoLogo -NoProfile -File .\scripts\reset-admin-password.ps1
```

Enter the project reference and exact existing administrator email, including its original letter case. Email and password values are not trimmed or normalized. Enter the new password twice at the masked SecureString prompts (the password characters are not displayed). The password must be well-formed Unicode, at least 15 Unicode characters, at most 72 UTF-8 bytes, nonblank and contain no NUL. Multibyte characters count toward the byte limit. It is hashed with the existing `bcryptjs` dependency at cost 12.

Finally type the exact confirmation phrase shown, `RESET PASSWORD <exact email> IN <V2 project reference>`. Anything else cancels before any database access. There is no `--yes` flag. The launcher requires an interactive terminal and passes the secrets through an anonymous stdin pipe, never arguments, temporary files, environment variables, or logs. Plaintext and hashes necessarily exist briefly in local process memory; close the terminal afterward. Clearing references does not guarantee memory erasure.

After validation and approval, a serializable transaction locks the exact user and related role, verifies the user exists and is active with role name `System Administrator`, then performs one parameterized update setting only that user's `password_hash`. Its update predicate repeats the identity, active status and role checks and requires exactly one returned ID. No accounts or roles are created, deleted or reassigned; `updated_at`, schema, tables and migrations are not modified by the utility. Locks and statement/connection timeouts bound concurrent access. Failures trigger rollback and connection cleanup, with no automatic retries.

Exit code 0 and `PASS` mean commit and cleanup completed. Exit code 1 means refusal or failure. Only sanitized status messages are printed. If commit acknowledgement, rollback or cleanup fails, the message explicitly says the outcome may be uncertain: verify privately before retrying. A connection loss during commit can occur after the server has committed; do not assume the old password still works. Check the private configuration for failures; never share raw database exceptions, credentials, password hashes or JWTs.

The reset does not invalidate already issued JWTs. Existing tokens retain their current lifetime. After a successful reset, the existing private `scripts/verify-admin-login.ps1` procedure can verify login with the new password. The operator previously reported a real recovery attempt and has now confirmed a successful System Administrator login against Supabase V2, including JWT and profile verification. That login result does not independently establish whether a particular recovery attempt committed. Codex has not run a real reset or repeated the real login. Automated tests use mocked database clients and PowerShell commands, with real local bcrypt and certificate parsing only.

Quality checks: `npm.cmd run quality` and `npm.cmd run audit`. Set `VERIFY_ADMIN_TEST_PWSH` to your PowerShell executable path if `pwsh` is not on PATH, so both PowerShell mock suites execute.

## Diagnosing a refused reset

The original `reset refused or failed; no commit requested` message covered every exception before the COMMIT attempt, provided rollback (when needed) and connection cleanup did not themselves fail. It did not identify which check failed. Entering the correct approval phrase satisfies only the approval check; it does not prove the password entries, project, connection, or account passed validation.

The utility now emits a fixed bracketed stage/reason, never raw exceptions or supplied values:

| Stage                 | Conditions that could produce the original failure                                                                                                                                                                                                                                                                                                                                                                    |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `INPUT_VALIDATION`    | Missing/nonobject input; invalid, blank, overlong, malformed Unicode, whitespace-containing or control-containing email; invalid project reference; password shorter than 15 Unicode characters, longer than 72 UTF-8 bytes, malformed Unicode, blank or containing NUL; different password confirmation; missing or different exact approval.                                                                        |
| `CONFIGURATION`       | Missing/malformed database URL or invalid percent encoding; non-PostgreSQL protocol; fragment; database other than `postgres`; missing database password; port other than 5432; query parameters other than exactly one `sslmode=verify-full`; disabled TLS verification; mismatched host/user/project reference; missing, unreadable, invalid or non-CA certificate. Extra URL parameters are intentionally refused. |
| `PASSWORD_HASHING`    | Local bcrypt hashing/randomness/runtime failure.                                                                                                                                                                                                                                                                                                                                                                      |
| `CLIENT_SETUP`        | Driver loading, client construction or event-handler setup failure.                                                                                                                                                                                                                                                                                                                                                   |
| `DATABASE_CONNECTION` | DNS, network, timeout, TLS certificate trust/validity/hostname, database authentication, pooler host/tenant mismatch, startup configuration or other connection refusal. Database credentials are separate from the application administrator password.                                                                                                                                                               |
| `TRANSACTION_BEGIN`   | Failure or timeout starting the serializable transaction.                                                                                                                                                                                                                                                                                                                                                             |
| `ACCOUNT_LOOKUP`      | Query, schema, permission, timeout or locking failure; zero or multiple joined rows; missing returned row; email not exactly equal; inactive account; role name not exactly `System Administrator`; nonpositive or nonsafe-integer user ID. The inner join also returns zero rows if there is no matching role.                                                                                                       |
| `PASSWORD_UPDATE`     | Query, permission, constraint, trigger, timeout, serialization or connection failure; returned row count other than one or unexpected user ID.                                                                                                                                                                                                                                                                        |

The column names and joins match the approved Prisma mappings (`users`, `roles`, `user_id`, `role_id`, `is_active`, `role_name`, `password_hash`). The recovery utility uses one `pg.Client` for BEGIN, lookup, update and COMMIT; it does not use Prisma's transaction API. Email case and whitespace are deliberately not normalized. Locks on the user and role, repeated update predicates and serializable isolation prevent a concurrent eligibility change from silently authorizing a reset. Matching the configured URL to an operator-supplied reference cannot establish that the operator copied the correct project's reference; obtain it independently from V2's dashboard.

Allowlisted driver classifications identify TLS problems, database authentication/permissions/schema, DNS/network failures, serialization conflicts, deadlocks and server cancellations/timeouts. Unknown errors show `DETAILS_WITHHELD` with their stage. Local client query timeouts and pooler errors without an allowlisted code may therefore show that fallback. Never enable raw logging to get a more detailed report. Wrapper failures have separate `WRAPPER/...` codes, including cancellation, private prompts, missing CA and native handoff; malformed stdin/JSON/startup failures retain their separate sanitized startup message. None of those wrapper/startup messages is the original inner reset failure above.

Failure during COMMIT reports an uncertain outcome; rollback or cleanup failures have their own warnings and may supersede the original stage. A mock explicitly reproduces a server commit followed by lost acknowledgement: the command fails although the password changed. `no COMMIT was sent by this run` describes only control flow, not an independent inspection of database state or previous attempts. There are no automatic retries.

Safest operator next step: use the existing private login verification command with the intended new password first. It reads application records and does not reset passwords. If it passes, no further reset is needed. If it fails, verify V2 configuration and exact account email privately, then run the recovery command only if you still intend to authorize a password change. Report only the bracketed stage/reason or sanitized verification stage; never share passwords, hashes, connection strings, credentials or raw errors. Do not infer from a failed login alone whether a previous reset committed, because login can also fail due to configuration or connectivity.
